# Gridiron StatScout: backend and data pipeline

Moved verbatim from AGENTS.md. Loads when a matching file is read; update it here.

- **Data source**: `nflreadpy` (nflverse) — weekly player stats + Next Gen Stats, cloud-IP friendly, no API key. See `handoff/NFL_CONTRACT.md` for the metric/category/schema contract.
- **Tables**: `player_snapshots` (id, season, season_type, PK (id, season, season_type); metrics/standard_stats/games jsonb; player_type ∈ qb/rb/wr/te/def). `player_game_logs` (PK (player_id, season, season_type, game_date, player_type); columns `game_id`, `plays`, `touches`, metrics jsonb). `player_recent_form` stores the league-anchored 3/5/8-week windows. Current publisher rows carry nullable `refresh_id`, `source_published_at`, and `published_at` metadata, so older rows and the existing app contract remain valid.
- **Categories** (jsonb `metrics[].category`, exact strings): `Passing`, `Rushing`, `Receiving`, `Defense`.
- **Supabase**: dedicated "Football" project ref `qwkmpwnhrejsuplcwxrb` (separate Supabase account from the other apps; Management API / CLI token does NOT reach it — apply schema via `psql` using `SUPABASE_DB_PASSWORD`). Creds in `~/.football_credentials` (SUPABASE_URL, SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY, plus `sb_publishable_`/`sb_secret_` keys and `SUPABASE_DB_PASSWORD`). Migrations in `supabase/migrations/`.
- **Data refresh workflows**: nightly `.github/workflows/nightly-statcast.yml` (name kept); manual `gh workflow run nightly-statcast.yml`. `STATCAST_SEASON` env var name kept for workflow compatibility; season = year if month ≥ 9 else year − 1.
- **Self-scheduled refresh** (as of 2026-09-14): GitHub cron is unreliable (no scheduled run fired for five hours on opening Sunday night, so SNF stats sat unpublished). Every refresh run ends with `schedule-next`, which dispatches `.github/workflows/refresh-timer.yml` with the planner's `wait_seconds`; the timer sleeps (max 5h45m, newest timer cancels older ones) and dispatches the refresh workflow with `planned=true`, so the planner decides rather than forcing. Cron (`7,37` in season, daily off season) is only a backup that restarts a broken chain. Manual dispatches without `planned` force a probe.
- **Advanced game pages**: after the publish step, `backend/ingest_game_details.py` rebuilds `public.game_details` (`20260914010000_game_details.sql`) from nflverse play-by-play: team and player EPA/success rate/CPOE/aDOT etc. as `{value, pct}` with percentiles ranked across the season's team games and qualifying player games, plus a win probability series and top WPA plays. `play_by_play_<season>.parquet` is in the probe fingerprint, so a pbp-only upload also triggers it.
- **Planner cadence**: the workflow fires every 15 minutes in September through February and once daily in March through August, and `backend/refresh_schedule.py` (stdlib, first step) decides whether the probe runs at all. It reads kickoff times from `public.games` (`20260914000000_games.sql`) and `last_checked_at`, and probes every 15m in the kickoff+3.5h to +8h window, hourly to +30h, every 3h to +4 days (enrichment), every 15m/30m/2h while a posted final has no `player_game_logs` rows (up to 5 days), else daily. It re-syncs `games` from nflverse `schedules/games.csv` (live and previous season) every 15m while a game is in progress, else daily. Planner errors fall through to probing. `workflow_dispatch` always forces both. The Games tab reads the same table.
- **Event-aware probe**: when the planner lets it run, `backend/source_probe.py` fingerprints the exact `stats_player_week_<season>.parquet` asset consumed by the builders, all three NGS assets, and PFR advanced defense (`games.parquet` is probed for readiness but left out of the fingerprint, since it republishes every ~30 minutes with no stat change). Unchanged probes are no-ops. `workflow_dispatch` supports `force=true` for a source correction with unchanged metadata. The workflow has a serialized `nfl-data-refresh` concurrency group with `cancel-in-progress: false`.
- **Atomic publication**: `backend/refresh.py` rebuilds the current season in full, stages snapshots, game logs, and Recent Form under one `refresh_id`, probes source metadata before and after the build, then calls `publish_data_refresh` from `20260912000000_event_aware_refresh.sql`. That RPC validates key uniqueness, coverage, same-season regression, and exact existing `game_id` retention before replacing the requested phases in one transaction. Failed or unstable builds leave the last live revision untouched. Successful stage payloads are deleted immediately, while lightweight run manifests are retained with bounded cleanup. Before staging, `refresh.py` hashes its output (ignoring `updated_at` and publish stamps); if the hash equals `data_refresh_state.last_success_content_hash`, it calls `mark_data_refresh_unchanged` (`20260913000000_skip_unchanged_refresh.sql`) instead, which records the new source fingerprint as handled and leaves rows, `refresh_id` and `published_at` untouched. nflverse re-uploads assets with no stat change several times a day, and republishing them made the app say "Updated 40m ago" about week-old numbers.
- **Freshness endpoint**: the app reads `public.data_refresh_status` through `/rest/v1/data_refresh_status?select=*&limit=1`. `refresh_id` identifies the live revision; `latest_refresh_id` identifies an in-flight or failed attempt. `source_published_at` and `published_at` describe source and database time separately. `max_week`, `max_game_date`, `expected_games`, `observed_games`, `coverage_status`, `ngs_status`, `pfr_status`, `last_checked_at`, and a short `last_error_code` make pending and degraded states explicit. During the September rollover, `season` is the latest probe/build target and can lead the last successful coverage; clients should label serving data from `refresh_id`, `published_at`, and coverage fields. The view excludes source payloads and internal error text.
- **Refresh runbook**: apply `supabase/migrations/20260912000000_event_aware_refresh.sql` with `SUPABASE_DB_PASSWORD` before dispatching the workflow. A source outage remains `source_pending` and is retried by the next probe. A failed builder keeps prior serving rows and records a retry-safe error code. Use `gh workflow run nightly-statcast.yml -f force=true` after checking logs when a correction has no metadata change. Do not remove live tables or the singleton state during diagnosis.
- **Recent Form covers the newest two seasons** (as of 2026-08-07): the live season and the one before it. `DashboardViewModel.recentFormSeasons` is the single source of truth; `supportsRecentForm` hides the Recent/Both controls on anything older (missing data, not a Pro upsell), and Trends offers exactly those two, with the older one behind the paywall like every other past season. Everything before that was purged once, taking the database from 441 MB to 110 MB; a season of `player_game_logs` + `player_recent_form` is ~26 MB, so 2025+2026 stays around 136 MB against a 500 MB budget.
- **`backend/prune_history.py` is a manual tool, not a nightly step** (as of 2026-08-07). Nothing in the pipeline writes an old season (both the game-log ingest and the rollup run against the resolved current season), so through the 2026 season the prune would have nothing to delete — a nightly DELETE that is always a no-op is pure risk, and it would have fired on the Sept 9 opener and dropped 2025 while the app still called 2025 live. `--keep` defaults to 2 to match `recentFormSeasons`; pruning to 1 empties Trends for last season. Run it in a later offseason if size ever justifies it. Re-ingest an old season with `ingest_game_logs.py --season N --full` + `rollup_recent_form.py --season N`. `psql` host is `db.qwkmpwnhrejsuplcwxrb.supabase.co` (user `postgres`); DELETE alone doesn't shrink the DB, `vacuum full` does.
- **Historical bundle**: `StatScout/Data/players-historical.plist` (34,331 rows: seasons 2000–2025 plus the season-0 career rollup, verified 2026-08-07) regenerated via `source ~/.football_credentials && python3 scripts/export_historical.py`. Past seasons are the *only* thing the bundle provides — nothing in the app fetches history over the network (`fetchHistoricalPlayers` exists but is unreachable), so a season missing here is missing from the app. Ahead of a rollover, fold the outgoing season in early with `STATCAST_SEASON=<next> python3 scripts/export_historical.py --historical-only`; `TwoTierPlayerCache.loadHistoricalPlayers` filters out any season that is still live, so such a bundle is safe to ship months before the calendar catches up. **No current-season snapshot ships in the bundle** (removed in 1.2.1): 1.2 bundled a four-team Week 1 export that the app served as the live leaderboard once a device's cache aged out. Always pass `--historical-only`; a `players-current` file the script writes is not a build resource.
